# Trellis 需求讨论

## 不可跳过的规划契约

要求构建、实施、修复、重构或“开始”，不等于批准离开规划阶段。创建任务的同意也不等于实施批准。

每个非简单任务开始实施前，用户必须在初始请求后至少回复一次。若无需澄清，该回复必须批准下文所述的最终规划总结。

只要仍有用户负责的产品、范围、UX、兼容性、风险或验收决策未解决，就以一个价值最高的问题结束本轮。不要编辑产品代码、分派实施或运行 `task.py start`。

## 不可跳过的证据规则

若问题可以通过查看代码库回答，就查看代码库。

这是强制要求。向用户提问前，先检查代码、测试、配置、文档、现有规范或任务历史中是否已有答案。

不要要求用户确认仓库可以回答的事实。只询问产品意图、偏好、范围、风险容忍度、验收行为，或查看证据后仍不明确的决策。

仓库证据确立当前行为与技术约束。用户期望的行为、功能范围边界和 UX 偏好，即使已有模式，也不能仅靠仓库证据回答；现有模式只能作为选项与建议依据，不能代替决策。

---

在阶段 1 规划中使用此技能，将用户请求转化为明确需求与规划产物。

## 前提条件

仅在用户已同意创建任务，并准备进入 Trellis 规划时使用此技能。

若任务尚不存在，创建任务：

```bash
TASK_DIR=$(python3 ./.trellis/scripts/task.py create "<short task title>" --description "<one-line summary>" --slug <slug>)
```

从用户请求中提取简短标题。标题与 `--description` 都不能为空；`create` 会拒绝空值，归档时也拒绝任一字段为空的记录。slug 不带日期前缀，`task.py create` 自动添加 `MM-DD-` 目录前缀。

`task.py create` 创建默认 `prd.md`。追问前，先根据当前理解更新该文件。

## 规划流程

1. 将用户请求与初步已知事实写入 `prd.md`。
2. 提问前查看现有证据：
   - 代码、测试、fixture 与配置
   - README、文档、现有规范与领域记录
   - 若存在，读取相关 Trellis 任务、研究文件和会话历史
3. 将发现分为：
   - 已确认事实
   - 仍需用户明确的产品意图
   - 仍需用户明确的范围或风险决策
   - 可能不属于范围的事项
4. 若还有用户负责的决策，询问唯一一个价值最高的问题，附上建议与取舍，然后停止。不要在同一轮实施。
5. 用户每次回答后，更新 `prd.md`，重新整理决策清单，并从步骤 2 重复。
6. 没有用户负责的决策剩余后，为复杂任务创建或更新 `design.md` 与 `implement.md`。
7. 运行需求收敛关卡，再执行 PRD 收敛整理。
8. 展示最终规划总结并停止。不要在同一轮运行 `task.py start` 或编辑产品代码。
9. 只有后续用户消息明确批准最新规划总结，才授权运行 `task.py start` 并实施。若批准后产物发生实质变化，重新进行最终评审。

不要虚构项目专用的产品或规范层级。若仓库已有产品、领域或规范文档，就使用它们；若没有，就基于现有证据继续。

## 提问规则

每条消息只问一个问题。

每个问题必须包含：

- 需要做出的决策
- 答案为何重要
- 推荐答案
- 用户选择其他答案时的取舍

不要询问是否搜索、查看文件或继续讨论等流程问题。直接完成证据工作。只有剩余问题属于产品决策、偏好、范围边界或风险容忍度时才询问用户。

建议不等于默认选择。不要仅因用户要求实施，就代用户选择推荐的产品决策。

若请求与仓库证据已经解决所有决策，不要制造澄清问题。此时直接展示最终规划总结，但仍需要后续明确批准。

最终评审是必需的阶段转换关卡，不属于被禁止的流程问题。创建任务的同意、初始实施请求，以及最新最终总结之前的批准，都不能满足此关卡。

## 思考框架：第一性原理分析

当需求模糊、方案显得过度设计，或准备“因为大家都这样做”而增加复杂度时，先拆解到基本事实，再向上推导。

### 步骤 1：重新表述问题

去掉实施细节，用一句话表达。

> 不佳：“需要给用户资料接口添加 Redis 缓存”
> 更好：“用户资料数据加载太慢”

### 步骤 2：列出基本事实

哪些是确定事实，而非意见或惯例？

| 类别 | 示例 |
|----------|----------|
| **物理约束** | 网络延迟 ≥ 0，磁盘 I/O 有上限 |
| **业务规则** | “用户必须看到自己的数据” |
| **技术不变量** | “数据必须一致” |
| **用户需求** | “用户希望在 Y 秒内得到 X” |

### 步骤 3：质疑假设

对当前计划的每个组成部分：

- **事实还是惯例？** “我们一直使用 REST” — 为什么？
- **去掉它会怎样？** 若没有任何损坏，它就不必要。
- **解决真实问题还是症状？** 追溯因果链。
- **谁从这份复杂度受益？** 若答案是“没人”，就简化。

### 步骤 4：从事实构建方案

1. 从满足全部事实的最小可行机制开始
2. 只有具体事实要求时才增加复杂度
3. 每项新增都必须回答：“哪条事实要求它？”

### 步骤 5：验证

- 方案是否解决原始问题？
- 哪些假设需要验证？
- 最简单的验证实验是什么？

## 需求收敛关卡

最终评审前，确认以下各项：

- 用户结果与产品价值明确
- 范围内与范围外行为明确
- 验收标准描述可观察结果
- 用户负责的产品、范围、UX、兼容性与风险决策均已解决
- 没有阻塞性的未决问题
- 技术未知项已研究，或明确延后且不改变 MVP 行为

轻量任务可以省略 `design.md` 与 `implement.md`，但不能跳过证据查看、需求收敛、最终评审或新的实施批准。

最终规划总结必须展示目标、范围内、范围外、验收标准、关键决策、相关风险或延后事项，以及产物状态。

## 产物规则

`prd.md` 记录需求与验收：

- 目标与用户价值
- 已确认事实
- 需求
- 验收标准
- 范围外事项
- 仍阻塞规划的未决问题

复杂任务的 `design.md` 记录技术设计：

- 架构与边界
- 数据流与契约
- 兼容性与迁移说明
- 重要取舍
- 运行或回滚考虑

复杂任务的 `implement.md` 记录执行规划：

- 有序实施清单
- 验证命令
- 高风险文件或回滚点
- `task.py start` 前的后续检查

轻量任务可以只有 `prd.md`。复杂任务运行 `task.py start` 前必须具备 `prd.md`、`design.md` 与 `implement.md`。

`implement.md` 不能替代 `implement.jsonl`。使用子代理分派工作流时，`task.py start` 前，`implement.jsonl` 与 `check.jsonl` 各自必须至少包含一个真实规范或研究条目；空清单或只有旧版 `_example` 占位行的清单不算。inline 工作流跳过此 JSONL 关卡，因为阶段 2 通过 `trellis-before-dev` 加载上下文。

## PRD 收敛整理

宣布规划就绪或运行 `task.py start` 前，按上述产物规则中的最终结构重写一次 `prd.md`。这不是可选整理，而是最终规划关卡。

整理必须无损：

- 将重复事实合并到一个权威章节。
- 将“目前已知”“假设”和已解决的“未决问题”等临时讨论章节并入目标、背景、需求、技术说明或验收标准。
- 删除已解决的未决问题，不保留空章节或已回答章节。
- 当缺陷清单与需求清单描述同一工作时，合并它们；保留每个缺陷的严重性、证据与文件:行号锚点，放在对应需求下。
- 保留所有文件:行号锚点、决策、约束、需求 ID 和验收标准映射。
- 仍有阻塞性未决问题时，不得进入最终评审。

整理后，从头到尾读取 `prd.md`，确认没有事实跨章节重复，除非重复带来新信息。

## 质量要求

宣布规划就绪前：

- `prd.md` 包含可测试的验收标准。
- `prd.md` 已完成收敛整理：没有未解决的临时讨论章节，没有跨章节重复事实，且没有丢失锚点、决策或验收映射。
- 仓库可以回答的问题已通过查看证据解决。
- 没有阻塞性未决问题。
- 复杂任务具备 `design.md` 与 `implement.md`。
- 子代理分派任务的 `implement.jsonl` 与 `check.jsonl` 都有真实且经过整理的条目；只有初始占位条目的清单尚未就绪。
- 已向用户展示最新最终规划总结。
- 用户已在后续消息中明确批准按该总结实施。

不要仅因用户最初要求实施，就开始实施。
