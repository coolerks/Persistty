# 打破循环 — 深入缺陷分析

调试完成后，使用此技能深入分析，打破“修复缺陷 → 遗忘 → 重复”的循环。

---

## 分析框架

从以下 5 个维度分析刚刚修复的缺陷：

### 1. 根因类别

缺陷属于哪一类？

| 类别 | 特征 | 示例 |
|----------|-----------------|---------|
| **A. 缺失规范** | 没有说明如何操作的文档 | 新功能没有检查清单 |
| **B. 跨层契约** | 层间接口不明确 | API 返回格式与预期不同 |
| **C. 变更传播失败** | 修改一处，遗漏其他位置 | 修改函数签名，遗漏调用点 |
| **D. 测试覆盖缺口** | 单元测试通过，集成失败 | 独立运行正常，组合后损坏 |
| **E. 隐含假设** | 代码依赖未记录的假设 | 时间戳秒与毫秒混淆 |

### 2. 修复为何失败（若适用）

若成功前尝试过多次修复，分析每次失败：

- **表面修复**：修复了症状而非根因
- **范围不完整**：找到根因，但没有覆盖所有情况
- **工具限制**：grep 未找到，类型检查不够严格
- **思维模型**：一直查看同一层，没有跨层思考

### 3. 预防机制

哪些机制可以防止再次发生？

| 类型 | 说明 | 示例 |
|------|-------------|---------|
| **文档** | 记录下来，让其他人知道 | 更新思考指南 |
| **架构** | 从结构上使错误不可能发生 | 类型安全的封装 |
| **编译期** | 严格类型检查，不留绕过入口 | 签名变化导致编译错误 |
| **运行时** | 监控、告警、扫描 | 检测孤立实体 |
| **测试覆盖** | E2E 测试、集成测试 | 验证完整流程 |
| **代码评审** | 检查清单、PR 模板 | “是否检查了 X？” |

### 4. 系统性扩展

此缺陷揭示了哪些更广泛的问题？

- **类似问题**：其他哪里可能存在同一问题？
- **设计缺陷**：是否存在根本的架构问题？
- **流程缺陷**：是否可以改进开发流程？
- **知识缺口**：团队是否缺少某种理解？

### 5. 知识记录

将发现固化到系统中：

- [ ] 更新 `.trellis/spec/guides/` 思考指南
- [ ] 更新相关 `.trellis/spec/` 文档
- [ ] 创建问题记录（若适用）
- [ ] 创建根本修复的功能任务
- [ ] 必要时更新检查指南

## 核心理念

> **调试的价值不只在修复缺陷，更在于使这一类缺陷不再发生。**

三个层次的洞见：
1. **战术**：如何修复这个缺陷
2. **战略**：如何预防这一类缺陷
3. **理念**：如何拓展思考模式

30 分钟分析可节省未来 30 小时调试。

## 思考框架：贝叶斯推理

多个根因都合理且证据不完整时，按新证据更新判断，不要固守初始假设。

### 步骤 1：建立先验

调查前，说明当前判断及理由：

| 假设 | 先验概率 | 理由 |
|------------|-------|-----------|
| H1：[原因 A] | 40% | 此模式中最常见 |
| H2：[原因 B] | 30% | 根据环境判断合理 |
| H3：[其他] | 30% | 包含其他可能性 |

先验概率总和必须为 100%。若无法分配概率，先调查。

### 步骤 2：观察证据

记录发现，具体说明可靠程度：

- 究竟观察到了什么？
- 有多可靠？（测试输出 > 日志消息 > 用户报告 > 直觉）
- 是否有多个假设可以解释它？

### 步骤 3：更新判断

对每个假设询问：**若此假设为真，出现这项证据的可能性有多大？**

更新方向比计算更重要：
- H1 强烈预测此证据 → H1 概率提高
- 证据与 H2 矛盾 → H2 概率降低
- 所有假设下证据同样可能 → 不更新

### 步骤 4：寻找区分性证据

不要重复收集同类证据。寻找在主要假设间**明显不同**的证据。

> 若 H1 与 H3 接近：“H1 为真而 H3 为假时，会看到什么？”然后检查这一点。

### 步骤 5：说明置信度

| 置信度 | 行动 |
|------------|--------|
| 90%+ | 执行修复并监控 |
| 70-90% | 执行修复，增加回退检查 |
| 50-70% | 提交前测试假设 |
| <50% | 需要更多证据，不要猜测 |

证据不完整时，不要表达非黑即白的确定性。使用“最可能”“合理但可能性较低”“值得调查”等表述。

### 常见谬误

| 谬误 | 示例 | 纠正 |
|---------|---------|------------|
| **忽视基础概率** | “测试失败 → 代码有问题” | 测试因其他原因失败的频率是多少？ |
| **确认偏误** | “肯定是竞态条件，让我找竞态证据” | 主动寻找反驳首要假设的证据 |
| **锚定效应** | “上次是缓存，这次大概也是缓存” | 根据当前上下文建立先验，而非昨天的缺陷 |

## 分析后的立即行动

> 本地项目边界：下列模板同步步骤适用于维护 Trellis 上游源码的仓库。本 Persistty 仓库没有 `src/templates/markdown/spec/` 或 `cross-platform-thinking-guide.md`，不要为执行示例而创建它们；将经验写入本项目现有 owner spec。提交仍遵循 `.trellis/workflow.md` 阶段 3.4 的提交方案与用户确认，不因本节示例自动提交。

**重要**：完成上述分析后，必须立即：

1. **更新规范或指南** — 不要只列 TODO，实际更新相关文件：
   - 跨平台问题 → 更新 `cross-platform-thinking-guide.md`
   - 跨层问题 → 更新 `cross-layer-thinking-guide.md`
   - 代码复用问题 → 更新 `code-reuse-thinking-guide.md`
   - 领域专用问题 → 更新 `backend/*.md` 或 `frontend/*.md`

2. **同步模板** — 更新 `.trellis/spec/` 后，同步到 `src/templates/markdown/spec/`

3. **提交规范更新** — 这是主要输出，而不只是分析文本

> **分析只停留在聊天里就没有实际价值，价值在于更新后的规范。**
