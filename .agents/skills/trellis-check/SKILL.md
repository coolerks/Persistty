# 代码质量检查

全面验证最近编写的代码，结合规范遵循、跨层安全与提交前检查。

---

## 步骤 1：确定修改内容

```bash
git diff --name-only HEAD
git status
```

## 步骤 2：读取任务产物与适用规范

按顺序读取当前任务产物：

- `prd.md`
- 若存在，读取 `design.md`
- 若存在，读取 `implement.md`

```bash
python3 ./.trellis/scripts/get_context.py --mode packages
```

对每个修改的包或层，读取规范索引，并遵循其中的 **“质量检查”（Quality Check）**章节：

```bash
cat .trellis/spec/<package>/<layer>/index.md
```

读取索引引用的具体规范文件；索引只是指针，不是阅读目标。

## 步骤 3：运行项目检查

运行项目的 lint、类型检查和测试命令。继续前修复所有失败。

## 步骤 4：按清单评审

### 代码质量

- [ ] lint 是否通过？
- [ ] 类型检查是否通过（若适用）？
- [ ] 测试是否通过？
- [ ] 是否没有遗留调试日志？
- [ ] 是否没有抑制警告或绕过类型安全？

### 测试覆盖

- [ ] 新增函数 → 是否添加单元测试？
- [ ] 缺陷修复 → 是否添加回归测试？
- [ ] 行为变化 → 是否更新现有测试？

### 规范同步

- [ ] `.trellis/spec/` 是否需要更新？（新模式、约定、经验）

> “若修复缺陷或发现不明显的行为，是否应记录下来，避免未来再次遇到？” → 若是，更新相关规范文档。

### 范围纪律

- [ ] 是否整理了任务并不要求修改的代码？
- [ ] 是否为尚不存在的场景添加了抽象、配置或扩展点？
- [ ] 是否为不可能出现的状态添加了推测性的回退逻辑？
- [ ] 是否修改了验收标准未提及的文件？
- [ ] 是否在调用者处添加绕过措施，而未修复行为实际归属的位置？

## 步骤 5：跨层维度（若适用）

若修改局限于单层，跳过此步骤。

### A. 数据流（修改涉及 3 个及以上层）

- [ ] 读取流是否正确：存储 → 服务 → API → UI？
- [ ] 写入流是否正确：UI → API → 服务 → 存储？
- [ ] 类型与 schema 是否正确地跨层传递？
- [ ] 错误是否正确地传递给调用者？

### B. 代码复用（修改常量、创建工具函数）

- [ ] 创建前是否搜索过现有类似代码？
  ```bash
  grep -r "pattern" src/
  ```
- [ ] 若同一值重复出现，它是否代表一个稳定概念，且调用者必须一起变化？只有此时才提取复用；仅仅当前恰好相同的两个字面量应保持分离。
- [ ] 批量修改后是否更新了所有出现位置？

### C. 导入与依赖（创建新文件）

- [ ] 导入路径是否正确（相对路径与绝对路径）？
- [ ] 是否没有循环依赖？

### D. 同层一致性

- [ ] 其他使用同一概念的位置是否一致？

---

## 步骤 6：报告与修复

报告发现的每个违规项，然后：

- 机械性的局部问题（lint 小问题、缺失类型、错误导入、死分支、失败断言）→ 原地修复，再重新运行项目检查。
- 涉及设计或判断的问题（共享概念命名、移动模块边界、改变公共接口、重新分配行为归属）→ 记录证据与建议，然后停止。不要悄悄重写。

若修复需要触及当前任务范围外的文件，说明情况并停止，不要扩大修改范围。
