# 触发模式

以下用户表达应让 AI 想到使用 `trellis mem`。用这些示例校准判断；若用户消息符合模式却没有使用 `mem`，可能遗漏了明显的历史检索机会。

模式按表达背后的*意图*分类，而非表面词语。同一意图可通过不同语言和表达风格出现。

## 回忆过去的解决方案

用户在问“我们或我之前如何解决的”。历史对话保存答案；代码库展示结果，却不一定包含推理。

- “上次我们是怎么解决的？”
- “关于 X，最后采取了什么措施？”
- “我们已经处理过一次了，对吗？”
- “上次怎么解的?”
- “之前是怎么搞定 X 的?”
- “我记得以前修过类似的”

使用：`trellis mem search "<symptom keyword>" --global --limit 10`，再对最接近的命中执行 `context`。

## 检索决策

用户引用存在于旧对话而非已提交文件中的决策。查看需求讨论窗口。

- “关于 X 的决定是什么？”
- “当时决定用 Postgres 还是 SQLite？”
- “选择 X 而非 Y 的理由是什么？”
- “我们当时为啥选了 X 而不是 Y?”
- “关于 X 我们之前是怎么定的?”
- “之前讨论过 X 的方案吗?”

使用：`trellis mem search "<decision keyword>"` 找到会话，再以 `extract <id> --phase brainstorm` 恢复讨论。

## 跨会话继续

用户间隔一段时间后恢复工作，上下文隐含在历史中。

- “我们做到哪里了？”
- “从上次继续。”
- “接着之前停下的位置做。”
- “继续上次的”
- “我们上次做到哪了”
- “接着昨天那个任务”

使用：`trellis mem list --task <current-task-dir>` 找到活动任务关联的最近会话，再 `extract` 最后一个。

## 调试熟悉的缺陷

当前缺陷似乎以前见过。历史会话可能保存了解决路径。

- “我感觉以前遇到过这个。”
- “这是不是上个月那个缺陷？”
- “和 X 中遇到的超时类似。”
- “这个错好像之前见过”
- “这个 bug 是不是上次那个?”
- “怎么又是这个 error?”

使用：`trellis mem search "<error message fragment>" --global`。选取实际错误字符串中短小且有辨识度的片段定位。

## 识别自己的重复模式

用户询问是否一直重复同类错误或决策。

- “我总犯这个错误吗？”
- “遇到 X 的频率有多高？”
- “这对我而言是反复出现的问题吗？”
- “我每次都踩这个坑吗?”
- “我老犯这个错?”
- “这类问题之前出现过几次?”

使用：`trellis mem search "<topic>" --global --limit 50`，查看列表中的日期与项目。必要时 `extract` 两三个会话作比较。

## 收尾回顾（按需）

用户明确希望回顾本任务，仅在用户要求时执行，不作为强制步骤。

- “总结一下本任务做了什么。”
- “关键决策和意外发现是什么？”
- “写下这一轮的经验。”
- “总结一下这次的经验”
- “记一下这次踩的坑”
- “复盘下这个任务”

使用：从 `.trellis/.runtime/sessions/*.json` 或 `mem list --task <task-dir>` 确定当前任务的会话 id，再执行 `extract <id> --phase brainstorm` 与 `--phase implement`。展示总结，尽可能提供具体文件:行号引用。是否再将总结写到 PRD、规范或笔记文件，由用户决定；可以提议，不要自动写入。

## 反模式：这些情况不使用 `mem`

- “这个函数做什么？” → 读取文件。
- “这个测试为何失败？” → 读取测试输出与文件。
- “代码库中 X 的正确模式是什么？” → grep 或读取规范文件。
- “Y 的最新 npm 版本是什么？” → 调用 `npm view`。
- “修复这个缺陷。” → 调试。只有怀疑存在历史上下文时才使用 `mem`，否则它只是噪声。

标准不变：资深同事回答前是否会问“我们是不是已经讨论过这个”？若会，使用 `mem`；若不会，不使用。
