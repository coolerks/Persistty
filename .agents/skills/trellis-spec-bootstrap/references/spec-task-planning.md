# 规范任务规划

默认使用单代理执行模型。代理可以创建 Trellis 任务以便追踪，但技能不应要求特定平台、CLI 或并行 worker 模型。

## 拆解

围绕真实责任边界创建规范工作单元：

- 包有自身约定时，以一个包为单元。
- 同一包具有不同前端、后端、CLI、worker 或共享库规则时，以一个层为单元。
- 模式跨越多个包且不属于某一层时，以一个跨领域指南为单元。

避免人为拆解。小型库通常只需要一次聚焦的规范编写，不需要多个任务。

## 任务结构

Trellis 任务有帮助时，使用以下章节编写简短 PRD：

```markdown
# 完善 <包或层> 的 Trellis 规范

## 目标
为 <范围> 编写项目专用的 `.trellis/spec/` 指南。

## 范围
- 规范目录：
- 需要查看的源码目录：
- 需要查看的测试：
- 范围外事项：

## 架构上下文
总结仓库分析中的具体发现。

## 待创建或更新的文件
- `.trellis/spec/.../index.md`
- `.trellis/spec/.../<topic>.md`

## 规则
- 根据真实代码库调整规范文件集合。
- 使用真实源码示例，附文件路径。
- 删除不适用的纯模板章节。
- 除非任务明确要求，否则不要修改产品源码。

## 验收标准
- [ ] 规范包含仓库中的具体示例与反模式。
- [ ] 不遗留占位文本。
- [ ] 索引文件与最终规范文件一致。
- [ ] 论断由源码、测试或项目文档支撑。
```

## 可选辅助代理

若宿主支持子代理，辅助代理可查看独立包或执行验证。它们是可选的；主代理仍负责集成与最终质量。

辅助任务必须有明确责任范围：

- 只读研究任务可以查看所分配范围需要的任何源码。
- 写入任务应负责互不重叠的规范目录。
- 验证任务应检查占位内容删除、失效链接与一致性。

不要在技能中固定辅助代理名称、供应商专用命令或平台专用路由。只将必需工作与验收标准写入任务。
