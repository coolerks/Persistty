# 规范编写

Trellis 规范是供未来代理使用的编码指南。应解释如何在当前仓库中工作，而非通用项目可能如何组织。

## 基于证据编写

每条重要规则应由以下某项支撑：

- 展示推荐模式的源码文件。
- 展示预期行为的测试文件。
- 定义约定的项目文档。
- 多个文件中反复出现的模式。

只有使规则更清楚时才使用简短片段。优先链接文件路径并说明符号或行为。

## 文件结构

使规范树与项目一致：

- 保留 `index.md` 作为规范目录的导航文件。
- 开发者会独立查找的主题应拆分。
- 不同文件会重复同一规则时应合并主题。
- 删除不适用的模板文件。
- 为模板遗漏的重要本地模式添加新文件。

## 内容标准

良好的规范章节包含：

- 规则何时适用。
- 应遵循的本地模式。
- 证明模式的源码或测试文件。
- 常见错误或反模式。
- 若具备项目针对性且可靠，提供验证命令或检查。

避免：

- 占位说明。
- 通用框架建议。
- 只在某个代理宿主中可用的工具指令。
- 长篇复制的代码块。
- 基于单一偶然实施细节制定规则。

## 示例结构

```markdown
## 命令处理器

命令处理器应将参数解析、验证与副作用分离。本地模式是：

- 在命令边界解析 CLI 参数。
- 调用核心逻辑前，将原始输入转换为带类型的任务选项。
- 将文件系统写入放在命令或服务层，而非模板辅助函数中。

参考文件：
- `packages/cli/src/commands/example.ts`
- `packages/cli/test/commands/example.test.ts`

避免向共享辅助函数传入原始 `process.argv` 或未经验证的配置对象。
```

## 最终检查

结束前：

```bash
grep -R "To be filled\\|TODO: fill\\|placeholder" .trellis/spec
```

还应检查链接、索引文件，以及是否有规范仍在描述模板而非当前仓库。
