# 更新代码规范 — 记录可执行契约

从调试、实施或讨论中获得重要知识时，使用此技能更新相关代码规范文档。

**时机**：完成任务、修复缺陷或发现新模式之后

---

## 代码规范优先规则（关键）

本项目中，实施工作的“spec”指**代码规范**：
- 可执行契约，而非只有原则的文本
- 具体签名、载荷字段、环境变量键与边界行为
- 可测试的验证与错误行为

若修改涉及基础设施或跨层契约，必须达到代码规范的深度。

### 强制触发条件

修改包含以下任一项时，应用代码规范深度：
- 新增或修改命令或 API 签名
- 跨层请求或响应契约变化
- 数据库 schema 或迁移变化
- 基础设施集成（存储、队列、缓存、密钥、环境配置连接）

### 必需输出（7 个章节）

触发上述条件的任务，包含以下全部章节：
1. 范围与触发条件
2. 签名（命令 / API / DB）
3. 契约（请求 / 响应 / 环境变量）
4. 验证与错误矩阵
5. 正常 / 基础 / 错误用例
6. 所需测试（含断言点）
7. 错误与正确示例（至少一对）

---

## 何时更新代码规范

| 触发条件 | 示例 | 目标规范 |
|---------|---------|-------------|
| **实现功能** | 新增集成或模块 | 相关规范文件 |
| **做出设计决策** | 选择可扩展模式而非简单方案 | 相关规范与“设计决策”章节 |
| **修复缺陷** | 发现错误处理的细微问题 | 相关规范（例如错误处理文档） |
| **发现模式** | 找到更好的代码组织方式 | 相关规范文件 |
| **遇到陷阱** | 得知必须先做 X 再做 Y | 相关规范与“常见错误”章节 |
| **建立约定** | 团队同意命名模式 | 质量指南 |
| **新增思考触发条件** | “做 Y 前别忘了检查 X” | `guides/*.md`（作为检查项） |

**关键认识**：代码规范更新不只针对问题。每次功能实施都包含未来 AI 或开发者需要安全执行的设计决策与契约。

## 规范结构概览

```
.trellis/spec/
├── <layer>/           # 各层编码标准（例如 backend/、frontend/、api/）
│   ├── index.md       # 概览与链接
│   └── *.md           # 按主题划分的规范
└── guides/            # 思考检查清单（不是编码规范！）
    ├── index.md       # 指南索引
    └── *.md           # 按主题划分的指南
```

### 关键区别：代码规范与指南

| 类型 | 位置 | 用途 | 内容风格 |
|------|----------|---------|---------------|
| **代码规范** | `<layer>/*.md` | 告诉 AI “如何安全实施” | 签名、契约、矩阵、用例、测试点 |
| **指南** | `guides/*.md` | 帮助 AI 判断“应思考什么” | 检查清单、问题、规范指针 |

**判断规则**：问自己：

- “这是**如何编写**代码” → 放入规范层目录
- “这是编写前**需要考虑什么**” → 放入 `guides/`

**示例**：

| 学到的内容 | 错误位置 | 正确位置 |
|----------|----------------|------------------|
| “此任务使用 API X，而非 API Y” | ❌ `guides/`（对思考指南过于具体） | ✅ 相关规范文件（具体约定） |
| “做 Y 时记得检查 X” | ❌ 规范文件（对规范过于抽象） | ✅ `guides/`（思考检查清单） |

**指南应是指向规范的简短检查清单**，不要重复详细规则。

## 更新流程

### 步骤 1：确定学到的内容

回答以下问题：

1. **学到了什么？**（具体说明）
2. **为什么重要？**（防止什么问题？）
3. **应放在哪里？**（哪个规范文件？）

### 步骤 2：分类更新类型

| 类型 | 说明 | 行动 |
|------|-------------|--------|
| **设计决策** | 为何选择方案 X 而非 Y | 添加到“设计决策”章节 |
| **项目约定** | 本项目如何做 X | 添加到相关章节，附示例 |
| **新模式** | 发现可复用的方法 | 添加到“模式”章节 |
| **禁止模式** | 会导致问题的做法 | 添加到“反模式”或“禁止做法”章节 |
| **常见错误** | 容易发生的错误 | 添加到“常见错误”章节 |
| **约定** | 达成共识的标准 | 添加到相关章节 |
| **陷阱** | 不明显的行为 | 添加警告提示 |

### 步骤 3：读取目标代码规范

编辑前，读取当前代码规范以便：
- 理解现有结构
- 避免重复内容
- 找到合适的更新章节

```bash
cat .trellis/spec/<category>/<file>.md
```

### 步骤 4：执行更新

遵循以下原则：

1. **具体**：提供具体示例，不只是抽象规则
2. **解释原因**：说明防止的问题
3. **展示契约**：添加签名、载荷字段与错误行为
4. **展示代码**：为关键模式添加代码片段
5. **保持简短**：每个章节只讲一个概念

### 步骤 5：更新索引（若需要）

若新增章节或代码规范状态变化，更新对应类别的 `index.md`。

## 更新模板

### 基础设施或跨层工作的必需模板

```markdown
## 场景：<名称>

### 1. 范围与触发条件
- 触发条件：<为何需要代码规范深度>

### 2. 签名
- 后端命令 / API / DB 签名

### 3. 契约
- 请求字段（名称、类型、约束）
- 响应字段（名称、类型、约束）
- 环境变量键（必需 / 可选）

### 4. 验证与错误矩阵
- <条件> -> <错误>

### 5. 正常 / 基础 / 错误用例
- 正常：...
- 基础：...
- 错误：...

### 6. 所需测试
- 单元 / 集成 / E2E 测试及断言点

### 7. 错误与正确示例
#### 错误
...
#### 正确
...
```

### 添加设计决策

```markdown
### 设计决策：[决策名称]

**背景**：要解决什么问题？

**考虑过的选项**：
1. 选项 A - 简短说明
2. 选项 B - 简短说明

**决策**：选择选项 X，因为……

**示例**：
\`\`\`typescript
// 实施方式
代码示例
\`\`\`

**可扩展性**：未来如何扩展……
```

### 添加项目约定

```markdown
### 约定：[约定名称]

**内容**：简短说明约定。

**原因**：本项目为什么这样做。

**示例**：
\`\`\`typescript
// 如何遵循此约定
代码示例
\`\`\`

**相关内容**：相关约定或规范的链接。
```

### 添加新模式

```markdown
### 模式名称

**问题**：解决什么问题？

**方案**：简短说明方法。

**示例**：
\`\`\`
// 正确示例
代码示例

// 错误示例
代码示例
\`\`\`

**原因**：解释此方法为何更好。
```

### 添加禁止模式

```markdown
### 禁止：模式名称

**问题**：
\`\`\`
// 不要这样做
错误代码示例
\`\`\`

**不佳原因**：解释问题。

**替代做法**：
\`\`\`
// 应这样做
正确代码示例
\`\`\`
```

### 添加常见错误

```markdown
### 常见错误：描述

**症状**：出现什么问题

**原因**：为何发生

**修复**：如何纠正

**预防**：未来如何避免
```

### 添加陷阱

```markdown
> **警告**：简短说明不明显的行为。
>
> 详细说明何时发生及如何处理。
```

## 交互模式

若不确定更新什么，回答以下提示：

1. **刚刚完成了什么？**
   - [ ] 修复缺陷
   - [ ] 实现功能
   - [ ] 重构代码
   - [ ] 讨论方法

2. **学到了什么或做出了什么决策？**
   - 设计决策（为何选择 X 而非 Y）
   - 项目约定（如何做 X）
   - 不明显的行为（陷阱）
   - 更好的方法（模式）

3. **未来 AI 或开发者需要知道吗？**
   - 理解代码如何工作 → 是，更新规范
   - 维护或扩展功能 → 是，更新规范
   - 避免重复错误 → 是，更新规范
   - 纯粹一次性的实施细节 → 可以考虑跳过

4. **与哪个领域相关？**
   - [ ] 后端代码
   - [ ] 前端代码
   - [ ] 跨层数据流
   - [ ] 代码组织与复用
   - [ ] 质量与测试

## 质量检查清单

完成代码规范更新前：

- [ ] 内容是否具体且可执行？
- [ ] 是否包含代码示例？
- [ ] 是否解释原因，而不只是说明做法？
- [ ] 是否包含可执行签名与契约？
- [ ] 是否包含验证与错误矩阵？
- [ ] 是否包含正常 / 基础 / 错误用例？
- [ ] 是否包含所需测试与断言点？
- [ ] 是否放在正确的代码规范文件？
- [ ] 是否与现有内容重复？
- [ ] 新团队成员是否能理解？

## 与其他命令的关系

```
开发流程：
  学到知识 → `update-spec`（Trellis 命令）→ 知识已记录
       ↑                                  ↓
  `break-loop`（Trellis 命令）←──────────────────── 未来会话受益
  （深入缺陷分析）
```

- `break-loop`（Trellis 命令）— 深入分析缺陷，常常发现需要更新规范的内容
- `update-spec`（Trellis 命令）— 实际执行更新
- `finish-work`（Trellis 命令）— 提醒检查是否需要更新规范

## 核心理念

> **代码规范是持续演进的文档。每次调试、每次恍然大悟，都是让实施契约更明确的机会。**

目标是**组织记忆**：
- 一个人学到的知识，让所有人受益
- AI 在一次会话中学到的知识，保留到未来会话
- 错误转化为文档中的防护规则
