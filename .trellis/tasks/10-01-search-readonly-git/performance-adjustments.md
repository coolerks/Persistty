# Git 延迟与重复请求修复（2026-10-01）

## 问题与范围

用户反馈 Halo 的 git-baseline/status 每15秒反复请求，单次5秒以上，提交详情超时，比较8–9秒，历史受后台占用返回429。本轮主会话单代理处理 Git 快照成本、仓库定位和前端请求生命周期，不改变只读产品边界、HTTP DTO、终端生命周期或部署配置。

源 Halo 仓库仅安全读取，Git CLI 均运行在本次私有快照。元数据约96,327,558字节（28文件/15目录），工作树约18,002,901字节（3310文件/883目录）；真实仓库不执行 init/add/commit/status 等CLI，也不保存或替换其文件。

## 修复

1. Service 已发现位置映射最多1000项，每次仍校验项目版本、root和.git identity。baseline只查文件祖先并保持最内层/重叠根；不再每API扫描完整项目，也不重复发现一次。
2. 历史、refs、提交详情、暂存与提交比较只复制白名单元数据；baseline和本地引用补目标文件。HEAD/未暂存普通路径只补该文件，新增/改名仍完整扫描识别。完整status保留全部工作树、ignore和预算语义。
3. WalkSnapshotWithCopy 复用本目录的 no-follow 句柄；目录/文件读取后复验，Darwin openat逐组件打开替代重复遍历前缀；Linux仍openat2。config白名单值一次生成；元数据强版本复验流式丢弃内容，减少额外整包内存。
4. GitPanel取消定时status，打开/切视图/刷新时读取；刷新先完成发现，同一世代只读一轮。共享活跃基线、背景串行一个、focus/online/visibility有30秒冷却，失败不轮询重试；保存版本变化与明确刷新可更新HEAD。退出/最后订阅释放、Abort/旧世代结果拒绝保持。
5. 单文件目标拒绝任意大小写 `.git` 路径组件，避免覆盖私有元数据；所有对象依然安全复制，不用源硬链接或跨请求正文缓存。

## 缺陷分析（trellis-break-loop）

### 根因类别

E 隐含假设：把每次完整安全snapshot视为足够廉价，所有Git读取采用同一范围。D 测试覆盖缺口：小仓库功能与单接口通过，未验证92MiB元数据/3310文件与多编辑器后台轮询的组合。B 跨层成本：2个共享工具名额与两个15秒后台机制互相放大，取消UI请求无法抵消已发生的扫描成本。

### 修复收敛

只取消轮询会留下单请求长延迟；只用批量句柄首次仍约4秒status，且历史无关复制依旧不合理。按语义缩小范围与Darwin句柄实现一起修复后，历史/详情/比较明显下降。最终串行复测避免以同机并行测试负载误判改动。

### 预防机制

| 优先级 | 机制 | 完成项 |
| --- | --- | --- |
| P0 | 数据范围 | 无关大文件回归防止重返全树快照 |
| P0 | 请求生命周期 | 共享/串行/取消/失败冷却单测；浏览器无轮询及刷新去重 |
| P0 | 访问边界 | 父目录交换/链接哨兵、私有metadata保留路径、原metadata hash不变 |
| P1 | 规模与负载 | 显式本机只读性能测试，记录完整服务耗时，避免扩大并发或超时掩盖问题 |
| P1 | 规范 | 后端Git/文件owner、前端Git owner和跨层指南同步 |

需要完整范围的其他CLI（搜索/ZIP）仍有各自语义与上限；本轮不将单文件Git范围机械扩展给它们，也不重构无关功能。W06任务保持进行中。
